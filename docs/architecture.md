# Architecture

## Layout

```
apps/
  api/                      @app/api: Node + Hono + oRPC
    src/main.ts             process entry: loads env, opens + migrates the db, serves, drains
    src/env.ts              the only reader of process.env (Zod schema)
    src/app.ts              createApp(deps): oRPC on /rpc, a 500 for defects
    src/router.ts           root router: { system: systemRouter, ... }
    src/context.ts          Deps (db, now, lifecycle) and the per-request Context
    src/errors.ts           the errors every service shares, mapped by `respond`
    src/orpc/               implementer.ts (`os`), procedures.ts (`respond`), result.adapter.ts
    src/modules/<name>/     one folder per feature; index.ts is its public API (docs/backend.md)
    src/testing/            createTestApp() for API tests
  web/                      @app/web: React 19 SPA (conventions: docs/react.md)
    src/main.tsx            applies the theme, creates QueryClient + router, renders
    src/router.tsx          createRouter: preload on intent, pending timings, providers
    src/routes/             thin file routes (__root.tsx, index.tsx)
    src/routeTree.gen.ts    generated by `vp -C apps/web run routes`; committed, never edited
    src/features/<name>/    components/, hooks/, model/ (pure), api/ (data); index.ts = public API
    src/lib/                oRPC client, failure types, QueryClient, providers, *.adapter.ts
    src/testing/            renderWithApp(), rpcOutput() / rpcError() for component tests
packages/
  ui/                       @app/ui: design tokens (src/styles.css) + Base UI primitives
  result/                   @app/result: Result type, ok/err, fromThrowable/fromPromise
  contracts/                @app/contracts: Zod schemas + the oRPC contract + shared errors
  db/                       @app/db: createDb(), tryQuery, schema/ (no tables), migrations/, ./testing
tools/
  oxlint-plugin/            @app/oxlint-plugin: the repo's lint rules (repo/*)
  canary/                   @app/canary: lints violating samples with the root config (docs/testing.md)
  rename-scope/             @app/rename-scope: `node tools/rename-scope/src/main.ts <name>`
  workspace-check/          @app/workspace-check: every dependency is `catalog:` or `workspace:*`
e2e/                        @app/e2e: Playwright journeys (`pnpm e2e`), `pnpm test:postgres`;
                            imports no app code, starts them as processes (docs/testing.md)
.vite-hooks/pre-commit      `vp staged` (the `staged` block of the root vite.config.ts)
.claude/                    Claude Code project settings: allowed commands, format-on-edit hook
.github/workflows/ci.yml    `pnpm check` and `pnpm e2e` on pushes to main and pull requests
```

Workspace packages are consumed as TypeScript source: each `package.json` has
`"exports": { ".": "./src/index.ts" }` (`packages/db` also exports `./testing`). Vite, Vitest,
Node (native type stripping) and the type checker all read the source directly, so there is no
build step and no project references. The price is that every package's type check also checks
the source it imports, which is fine at this size. Keep code erasable (`erasableSyntaxOnly`: no
enums, no namespaces, no parameter properties) so Node can run it, and import relative files with
their `.ts` extension.

## Dependency rules

| Rule                                                                                            | Enforced by                                                                    |
| ----------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| A package can only import dependencies it declares                                              | pnpm strict `node_modules` + type check                                        |
| `apps/web` must not import `apps/api` or `packages/db`                                          | `repo/boundaries` (zones)                                                      |
| `packages/*` must not import `apps/*`                                                           | `repo/boundaries` (zones)                                                      |
| `packages/result`: no npm imports                                                               | `repo/boundaries` (externals, `PURE_PACKAGES`), `"types": []`                  |
| `packages/contracts`: only `zod`, `@orpc/contract`                                              | `repo/boundaries` (externals, `PURE_PACKAGES`), `"types": []`                  |
| `apps/api/src/modules/<x>` imported only via `modules/<x>/index.ts`                             | `repo/boundaries` (modules)                                                    |
| `apps/web/src/features/<x>` imported only via its `index.ts`                                    | `repo/boundaries` (modules)                                                    |
| Only `features/*/api/` and `src/lib/` use the oRPC client or the network                        | `repo/boundaries` (zone with `except`), `no-restricted-globals` (`fetch`, ...) |
| `features/*/model/`: no npm package but `zod` (workspace packages allowed); no clock or global  | `repo/boundaries` (externals), `repo/pure-model`                               |
| `src/lib/` imports no feature or route; features import no route                                | `repo/boundaries` (zones)                                                      |
| `packages/ui`: only React, Base UI, lucide-react, tailwind-variants; no other workspace package | `repo/boundaries` (externals, zone)                                            |
| `*.adapter.ts` imports no API module and no web feature                                         | `repo/boundaries` (zone)                                                       |
| No import cycles                                                                                | `import/no-cycle`, `import/no-self-import`                                     |
| Versions declared once, in `pnpm-workspace.yaml#catalog`                                        | `tools/workspace-check` (test); Knip for unused entries                        |

`repo/boundaries` lives in `tools/oxlint-plugin/src/boundaries.ts` and is configured in the root
`vite.config.ts` (`lint.rules["repo/boundaries"]`): `zones` (folders that may not import other
folders), `externals` (npm allowlists per folder; workspace packages are not npm imports) and
`modules` (roots whose subfolders are imported only through `index.ts`). It resolves relative
paths and workspace package names to repo paths, so it catches both `@app/api` and
`../../api/src/x.ts`. Test files are exempt from the externals allowlists so they can import
`vite-plus/test`. The pure packages are listed in `PURE_PACKAGES` in the root `vite.config.ts`,
with their npm allowlists. Their tsconfig keeps what `tsconfig.base.json` sets, `"types": []` and
no DOM lib, so Node and browser globals (`process`, `fetch`, `window`) are type errors there, and
`repo/pure-model` bans the clock and random sources in them.

Why these rules: an agent reads the files near the one it edits and copies what it sees. If a
component may call `fetch`, the next one will; if a feature may reach into another's internals,
the two become one feature with no seam. The rules keep each kind of code in one place, so
"where does this go" has one answer, and the answer is checked.

Lint, boundaries and type check all run in one oxlint pass (`vp check`). The canary
(`tools/canary`, `docs/testing.md`) proves that each boundary still fires at the paths it is meant
for.

## Recipes

Each step names the files to touch and the command that verifies it. Run `pnpm check` at the end
of every recipe, and `pnpm e2e` when a screen changed. The order below is the order the first
feature needs them: a table, an API module, a web feature (with a UI primitive if one is
missing). `docs/errors.md` has "Recipe: a contract error" and "Recipe: a shared error";
`docs/testing.md` has "Recipe: a lint rule and its canary case".

### Recipe: a table and its first migration

The template has no tables. `packages/db/src/schema/index.ts` is the schema entry drizzle-kit
reads (`packages/db/drizzle.config.ts`).

1. Add `packages/db/src/schema/<name>.ts` with the table. Give columns explicit snake_case names
   (the config sets no `casing`), name every constraint you will map to a domain error, and
   export the name as a constant so a repo compares with it, not with a string:

   ```ts
   import { pgTable, text, timestamp, unique, uuid } from "drizzle-orm/pg-core";

   export const NOTES_TITLE_UNIQUE = "notes_title_unique";

   export const notes = pgTable(
     "notes",
     {
       id: uuid("id").primaryKey().defaultRandom(),
       title: text("title").notNull(),
       body: text("body").notNull(),
       createdAt: timestamp("created_at", { withTimezone: true }).notNull(),
     },
     (table) => [unique(NOTES_TITLE_UNIQUE).on(table.title)],
   );

   export type NoteRow = typeof notes.$inferSelect;
   ```

   IDs: the template has no ID package, so `defaultRandom()` (the database's `gen_random_uuid()`)
   is the simplest choice. If the client must know an ID before the server answers (optimistic
   writes), add a pure package with branded ID types and a `newId()` (UUIDv7) and use
   `uuid("id").$type<NoteId>()` instead. Timestamps have no default: the repo sets them from the
   context's `now` (`docs/backend.md`, "Context").

2. Export the table from `packages/db/src/schema/index.ts` and from `packages/db/src/index.ts`
   with named exports, so repos import it from `@app/db`:
   `export { notes, NOTES_TITLE_UNIQUE, type NoteRow } from "./schema/index.ts";`. Avoid
   `export *`: it would also re-export `DB_SCHEMA` from the package entry, which Knip reports as
   unused. Verify: `vp -C packages/db check`.
3. Generate the migration: `pnpm -C packages/db generate`. drizzle-kit writes
   `packages/db/migrations/<timestamp>_<name>/migration.sql` and `snapshot.json`. Read the SQL and
   commit both; never edit a migration once it has run anywhere but your machine.
4. Verify the migration applies: `vp -C packages/db test` (the test database is migrated from
   scratch whenever the migrations change) and `vp -C apps/api test`.
5. Add the repo functions in the module that owns the table (`<name>.repo.ts`, next recipe), with
   a test that asserts each mapped constraint.
6. Run `pnpm test:postgres` once (Docker): PGlite and Postgres agree on almost everything, and this
   is where they would not.

The API applies pending migrations at startup (`main.ts` calls `migrate()`); there is no separate
migrate command. `pnpm dev` keeps its data in `.data/pglite`; delete it after rewriting an
unshipped migration.

### Recipe: an API module

1. **Contract.** Add `packages/contracts/src/<name>.ts` exporting `export const <name> = { ... }`
   of procedures built with `oc.input(...).output(...).errors({...})` (copy
   `packages/contracts/src/system.ts`), and add it to `contract` in
   `packages/contracts/src/index.ts`. Declare every error the client should act on
   (`docs/errors.md`, "Recipe: a contract error"); reuse `SERVICE_UNAVAILABLE` from
   `./errors.ts` for procedures that touch the database. Export from the package's `index.ts`
   only what another package imports (the web's form needs the input schema, for example).
   Verify: `vp -C packages/contracts check`. `vp -C apps/api check` now fails with "Property
   '<name>' is missing" on `src/router.ts`: the router does not implement the new procedures.
2. **Shared errors.** The first module with a repo needs `unexpected()` in
   `apps/api/src/errors.ts`, mapped by `respond`: follow `docs/errors.md`, "Recipe: a shared
   error". Verify: `vp -C apps/api test src/orpc`.
3. **Repo.** `apps/api/src/modules/<name>/<name>.repo.ts`: queries only, `db` first, every query
   through `tryQuery`, its failures mapped to the module's errors, `Unavailable` and
   `Unexpected` (the example in `docs/backend.md`, "Repos").
4. **Service.** `<name>.service.ts`: functions that take the context, or a `Pick` of the fields
   they use (`Pick<Context, "db" | "now">`), and return `Result` with an explicit return type
   (`Promise<Result<T, TitleTaken | Unavailable | Unexpected>>`). Business rules go here; take the
   time from `now()`. Copy the shape of `modules/system/health.ts`.
5. **Router.** `<name>.router.ts`: `os.<name>.<procedure>.handler(...)` calling the service and
   mapping its result with `respond` (copy `modules/system/system.router.ts`), and `index.ts`
   exporting only the router: `export { notesRouter } from "./notes.router.ts";`.
6. **Mount** it in `apps/api/src/router.ts` (`notes: notesRouter`). Verify: `vp -C apps/api check`
   passes once the router matches the contract.
7. **Test.** `<name>.test.ts` through `createTestApp()`: the happy path with a pinned `now`, one
   test per declared error (including `SERVICE_UNAVAILABLE` with `db: unreachableDb()`), and one
   for invalid input (`BAD_REQUEST`). Copy `modules/system/system.test.ts`. Verify:
   `vp -C apps/api test src/modules/<name>`.
8. New dependencies for procedures (a mailer, a client for another service) go on `Deps` in
   `apps/api/src/context.ts`, are built in `main.ts`, get a default in
   `apps/api/src/testing/test-app.ts`, and tests pass their own through `createTestApp({...})`.

### Recipe: a web feature

`features/system` is the worked example of a read; this recipe adds a list and a form. Read
`docs/react.md` first.

1. **Folders.** Create `apps/web/src/features/<name>/` with `api/`, `model/`, `hooks/`,
   `components/` and `index.ts` (what routes and other features use).
2. **Failure types and words** in `model/<name>.ts`: name the procedures, word every failure in a
   `Record` (copy `features/system/model/health.ts`). Validation is a pure function over the
   contract's input schema (`docs/react.md`, "Forms"). `model/` may import `zod`, `@app/contracts`,
   `@app/result` and types from `lib/`, nothing else.

   ```ts
   export type ListFailure = ApiFailure<"notes.list">;
   export type CreateFailure = ApiFailure<"notes.create">;
   const CONFLICT: Record<Extract<CreateFailure, { type: "conflict" }>["reason"], string> = {
     title_taken: "Another note has this title. Choose a different one.",
   };
   ```

   Verify: `vp -C apps/web test --project unit` with `model/<name>.test.ts` next to it.

3. **Data** in `api/<name>.ts`, the only folder that imports `lib/orpc.ts`. Reads are query
   options; writes return a `Result` (copy `features/system/api/health.ts`):

   ```ts
   export const notesQuery = queryOptions<Note[], ListFailure>({
     queryKey: ["notes", "list"],
     queryFn: async () =>
       unwrapForQuery(await fromPromise(() => api.notes.list(), failureOf("notes.list"))),
   });
   export async function createNote(input: NoteFields): Promise<Result<Note, CreateFailure>> {
     return fromPromise(() => api.notes.create(input), failureOf("notes.create"));
   }
   ```

   The output type comes from the client: `type Note = Awaited<ReturnType<typeof api.notes.create>>`.
   Verify: `vp -C apps/web check` (a procedure the contract does not have does not compile).

4. **Hooks** in `hooks/use-<action>.ts`: a form action with `useActionState` that validates with
   the model, calls `api/`, maps a failure to form state with the model, and on success
   invalidates the query (`queryClient.invalidateQueries({ queryKey: notesQuery.queryKey })`).
5. **Components** in `components/<name>.tsx`, one exported component per file: `useQuery(...)`
   with pending (`Skeleton`), error (the model's sentence) and data branches; the form with
   labels tied to inputs by `htmlFor`/`id` (`useId()`), errors under their field, a request
   failure in a `role="alert"` above the submit button. If `@app/ui` lacks a primitive, add it
   with the next recipe.
6. **Route.** Add `apps/web/src/routes/<path>.tsx` that renders the feature's components and starts
   the data in the `loader` (`void context.queryClient.prefetchQuery(notesQuery)`; copy
   `routes/index.tsx`). Run `vp -C apps/web run routes` to regenerate `src/routeTree.gen.ts`.
   Verify: `vp -C apps/web check`.
7. **Component test** (`components/<name>.test.tsx`) for the behaviour: render with
   `renderWithApp(...)` (`src/testing/render-with-app.tsx`) and answer the API by stubbing
   `fetch` with `rpcOutput(value, datePaths)` and `rpcError(code, status, data)`
   (`src/testing/rpc-responses.ts`), so the real client, serializer and `failureOf` run. Find
   everything by role and label. Verify: `vp -C apps/web test`.
8. **Journey.** If the screen is something a user does, add `e2e/tests/<name>.spec.ts` that finds
   everything by role and name and creates what it asserts on with a unique name (journeys share
   one database). Verify: `pnpm e2e`.

### Recipe: a UI primitive

`packages/ui` keeps only the primitives the template's screens use (`Button`, `RadioGroup`,
`RadioCard`, `Skeleton`). Add the next one when a screen needs it, in the same change as that
screen (Knip reports an exported primitive nothing uses). Copy `packages/ui/src/button.tsx`:

1. One file per component, `packages/ui/src/<name>.tsx`, wrapping the Base UI part(s). The Base UI
   docs are in `packages/ui/node_modules/@base-ui/react/docs/react/components/<name>.md` (after
   `vp install`).
2. Styles in a `tv({...})` recipe at module level: `base`, `variants`, `defaultVariants`, `slots`
   for multi-part components. Tokens only (`repo/design-tokens`); if a value is missing, add a
   token to `packages/ui/src/styles.css`.
3. Props: `Omit<Base.Props, "className"> & VariantProps<typeof recipe> & { className?: string }`
   (also omit a native prop a variant shadows, such as `size` on an input). `ref` is a normal prop
   in React 19 and is already in `Base.Props`; spread `...props` last so Base UI's `render`
   composition works.
4. Export it and its props type from `packages/ui/src/index.ts`, with a one-line JSDoc on when to
   use it. Verify: `vp -C packages/ui check`.
5. Test the behaviour the component adds (keyboard, ARIA, states), not markup:
   `packages/ui/src/<name>.test.tsx`. Verify: `vp -C packages/ui test`.
6. A form control wrapped in a `<label>` is not seen as a control by
   `jsx-a11y/label-has-associated-control` (the rule does not know `Input` renders an `<input>`):
   tie the label with `htmlFor` and the control's `id` instead.

### Recipe: a package

1. Create `packages/<name>/` with `package.json` (copy `packages/result/package.json`, rename to
   `@app/<name>`), `tsconfig.json` (copy `packages/result/tsconfig.json`: it extends
   `../../tsconfig.base.json` with `"include": ["src"]`), and `src/index.ts`. A tool goes in
   `tools/<name>/` instead (copy `tools/rename-scope`) and gets an entry in `knip.config.ts`
   `workspaces`.
2. Scripts: `"check:static": "vp check"` and, with its first test,
   `"test": "vp test --no-cache --no-fsModuleCache"` (`docs/testing.md` explains the flags). The
   root `pnpm check` picks both up through `vp run -r`.
3. Dependencies: add the version to `catalog:` in `pnpm-workspace.yaml`, reference it as
   `"catalog:"`; internal ones as `"workspace:*"`. Run `vp install`. Verify:
   `vp -C tools/workspace-check test`.
4. If it must stay pure (no Node, no DOM, no IO), add it to `PURE_PACKAGES` in the root
   `vite.config.ts` with its npm allowlist, keep the base `"types": []` (no `"types": ["node"]` in
   its tsconfig), and add a canary
   sample to the pure-packages case in `tools/canary/src/cases/boundaries.ts` that imports
   something outside the allowlist (`docs/testing.md`, "Recipe: a lint rule and its canary
   case"). If it needs Node types, use `"types": ["node"]` and `@types/node` instead. If an app
   must not import it, add a zone.
5. Verify: `vp -C packages/<name> check`, then `pnpm check`. Knip reports the package's exports
   if nothing imports them yet; add its first user in the same change.
